## 0. 一句话结论

模拟交易下单失败**不是**行情数据算错了，而是 `market_quotes` 集合几乎是空的（仅 1 条），而行情同步任务被**四层叠加**关停（启动期环境变量 → 数据库偏好 → 代码查询条件 → cron 星期错位），且第三层即使打开也会返回 0 只标的。修复需分两阶段：**阶段 A 纯数据回填（零风险，立刻可用）**、**阶段 B 三处代码/配置修正（需重启 backend 一次）**。

#### 第 4 层：cron 表达式的星期错位

`app/core/config.py:297`：

```python
AKSHARE_QUOTES_SYNC_CRON: str = Field(default="*/30 9-15 * * 1-5", description="行情同步CRON表达式")
```

APScheduler 的 `CronTrigger.from_crontab` 中 **`0 = 周一`**，因此 `1-5` 实际是**周二至周六**，**周一永不触发**。

这个结论已于 2026-10-25 在容器内实测（APScheduler 3.11.3）：

```
基准 2026-10-24 周六 22:00
dow=1-5      -> next 2026-10-27 18:00 Tuesday    ← 当前配置
dow=mon-fri  -> next 2026-10-26 18:00 Monday     ← 正确
```

同文件的 `AKSHARE_HISTORICAL_SYNC_CRON`（line 299）已改为 `mon-fri` 并通过 10-26 18:00 的实跑验证。

## 4. 改动方案

### 阶段 A：数据回填，让全市场立刻可下单（零代码改动、零重启）

**目标**：把 `stock_daily_quotes` 里 10-26 的 5,566 只收盘快照灌进 `market_quotes`，让任意 A 股都能通过价格区间校验。

**为什么不直接用系统的 `backfill_from_historical_data()`**：它依赖 `DataSourceManager.find_latest_trade_date_with_fallback()`，会走外部数据源（可能撞 tushare 出站闸门或新浪限流）。用纯 MongoDB 脚本从已有历史数据聚合，**零外部依赖、可控、可验证、可回滚**。

**步骤**：

| # | 动作 | 说明 |
|---|---|---|
| A1 | 备份当前 `market_quotes` 唯一一条（159865） | 导出 JSON 到 `/home/ubuntu/k-tradingagents-paper-quotes-fix-20261027-v1/backup-market-quotes-20261027.json` |
| A2 | 删除该条 | 让集合归零，解除回填堵塞 |
| A3 | 从 `stock_daily_quotes` 聚合 10-26 全量 | 取 `symbol`/`code`、`close`、`high`、`low`、`open`、`pre_close`、`volume`、`amount`、`pct_chg` |
| A4 | 批量 upsert 到 `market_quotes` | 按 `{code: code6}` upsert，补 `symbol`/`trade_date`/`updated_at`/`data_source="historical_backfill"` |
| A5 | 重新写入 159865 | 用第 2.1 节的真实腾讯快照值（ETF 不在 `stock_daily_quotes` 内） |
| A6 | 抽样验证 | 随机 20 只，模拟 `_get_today_price_range` 的查询条件，确认 `high`/`low`/`close` 均存在且 >0 |

**预期结果**：`market_quotes` 从 1 条 → 约 5,567 条（5,566 只股票 + 1 只 ETF）。

**已知局限（必须在评审中确认可接受）**：
- 数据是 **10-26 收盘快照**，不是盘中实时价
- 交易时段内下单，价格区间校验用的是**前一交易日**的高低价 → 指定价格偏保守，可能误拒当日正常价格
- 市价单（价格留空）不受影响，会用 `close`=10-26 收盘价成交 → **成交价可能偏离当前市价**
- 这是应急措施，不是最终状态；阶段 B 生效后盘中会被实时数据覆盖（15 分钟新鲜度检查）

**回滚**：删除 `data_source="historical_backfill"` 的记录，恢复 A1 的备份文件。

## 5. 实施顺序（建议）

```
T+0  阶段 A（纯 DB）
      A1 备份 → A2 删除 → A3 聚合 → A4 upsert → A5 补 ETF → A6 验证
      ── 用户立刻可对任意 A 股下单，无需等待 ──

T+0  阶段 B1 改代码（写生产挂载文件，原地覆盖保 inode）
T+0  阶段 B2 改配置（同上）
T+0  重启 backend（约 30 秒，健康检查恢复后继续）
T+0  阶段 B3 走 API 打开 akshare_quotes_sync
T+0  手动 trigger 一次，观察日志与写入结果
T+1  次日 9:00~15:30 观察定时执行（cron 修正后的首次自然触发）
```

**为什么重启不用 `up -d`**：B1/B2 只改挂载源文件内容，compose 的挂载定义不变，`docker restart` 即可让 Python 重新加载模块。若用 `up -d`，需带齐 13 个 `-f` 文件与 `--profile cutover-approved`，风险更高。

**为什么不能用 `mv` 替换挂载文件**：文件级 bind mount 绑定的是 inode，`mv` 会换新 inode 而容器仍持有旧 inode（10-26 已踩过，容器内 `grep` 计数为 0）。**必须用 `cp` / `shutil.copyfile` 原地覆盖。**
