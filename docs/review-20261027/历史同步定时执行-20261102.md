## 实现

- `app/worker/tushare_sync_service.py::run_tushare_historical_sync` 直接等待现有批次服务，定时只接受 `incremental=True`。手动按钮仍走同一个批次、库存、写入契约、断点及累计额度。
- `app/services/tushare_history_schedule.py` 要求运维单独安装 0600 的调度许可，绑定当前 generation 和政策哈希；只接受工作日 18:30、Asia/Shanghai。无许可、过期、STOP、政策不符均不能开启。不提供 HTTP 续期功能。
- 日历只接受当天 AKShare 证据；周末、盘前、假日和无法确认日历均记录跳过，不调用 Tushare 日历。交易日执行前持久保留当天占位，失败不自动重跑；连续单股超时仍只有原先最多三次尝试，每次计费。
- 新执行记录统一沿用调度器的 naive 北京时间，避免 BSON 自动转为 UTC 后被现有 30 分钟活动查询/僵尸检测误判；不改写旧记录。定时遇到仍未完成的旧计划也必须先人工核查，不静默恢复旧日期。
- 全程共用跨代 admission 文件锁；APScheduler 保留单实例、合并错过触发、仅容许 300 秒误点宽限。定时批次在遇到请求、库存或写入问题时关闭本代闸门，不在翌日自动恢复。
- `scheduler_runtime.py` / `tushare_manual.py` 仅在有效调度许可下保留历史任务的显式偏好。其余四个任务继续强制关闭。持久化失败恢复触发器、暂停状态及并发选项。
- `scheduler_service.py` 不再为已经写入详细终态的历史批次额外插入一条泛化成功记录；历史任务修改 cron 也不能绕过许可或顺带启用暂停任务。

## 交付顺序与失败边界

1. 提交后 `prepare_history_schedule.py --action freeze` 固定六个源码及 Compose；新增三个只读挂载、替换三个已有来源，backend **40→43**。旧来源及镜像不覆盖，frontend 不重建。
2. `--action prepare` 只暂存、备份并核验当前生产。备份原 Compose、源码、封印和状态哈希；取得两个历史子集完整原始 BSON 的排序哈希，仅把哈希带回本机。候选源码显式设 0644，以真实 uid/gid 在无网络、无生产秘密/数据卷的同镜像导入完整 `app.main`。这不等于真实启动或上游验收。
3. `run_history_schedule_switch.py --action freeze-controller` 固定停机包。`--action check` 使用独立尝试目录做完整不停机预检和鉴权核验。预检不能恢复定时任务，也不调用数据 API。
4. 获得具体包的停机/续期授权后，唯一一次 `--action execute` 重建 backend，校验健康、实际挂载/镜像/源码、封印、正常鉴权、前端原内容、相关集合及偏好。任何失败按原 Compose 链回滚；回滚失败请求停止 backend 并保留现场。
5. `renew_history_transport.py --action prepare` 提前备份本机授权/timer/固定配置并校验候选；`--action apply` 只在授权后执行。保留原文件 owner/group/mode，额外以实际转发用户验证可读；核对 systemd 下一次到期时间，失败恢复原文件和 timer。
6. `run_history_schedule_opening.py --action freeze` 固定独立启用包。获授权后只执行一次 `execute`：要求成功上线回执与续期成功；生产内完整备份两个 Tushare 子集 BSON、索引、调度偏好与 generation 账本，哈希读回；原计划逐股对账；停止前代后新建有限期 generation，原累计与每日计数逐项校验继承。然后创建调度许可，经正常鉴权 resume API 开启历史任务。
7. 启用工具会在第一轮到期至少 10 分钟前，另做一次 backend 正常重启并校验历史偏好和 18:30 cron 保留、其余四个任务暂停。重启验收失败关闭新 generation；不自动删除数据、不恢复旧预算、不重跑启用工具。
