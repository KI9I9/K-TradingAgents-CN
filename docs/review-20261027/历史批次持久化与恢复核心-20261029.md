# 历史批次持久化与恢复核心（2026-10-29）

本轮完成本地执行核心，不是生产执行器上线。新增 `deploy/history_batch_journal.py`；没有生产连接、上游请求、正式入库、许可重置或任务启用。生产仍使用已经验收的入口拒绝版本。

## 已实现

- 显式创建权限 700 的工作目录、600 的文件；原目录/原计划再次创建会失败，不重置状态。
- 冻结整个计划，计划哈希、股票代码和观察哈希贯穿全程；不用动态股票池的整数下标恢复。
- 同一个工作目录的所有批次共用一个非阻塞 `flock`，持有到当前批次切片结束。没有 force 绕锁入口。
- 每只股票独立原子 JSON 记录；临时文件 fsync → replace → 目录 fsync。响应内容和响应哈希与 fetched 状态同时落盘。
- 不提供生产执行 CLI。调用方必须显式提供六个适配接口和 `max_items`，默认没有任何出站/入库能力。
- 新增永久 STOP 标记，不等运行锁即可设置；在取数、写入和核验边界检查。无法撤回已发出的请求；没有删除 STOP 的接口。

| 持久化状态 | 含义 | 重新进入时的动作 |
|---|---|---|
| pending | 尚未开始取数 | 重新检查授权和同源库存观察，才可开始 |
| fetching | 已在调用取数前落盘；可能发出过请求 | 整批停止，不能自动重发；后续股票也不继续 |
| fetched | 已保存并验证完整结果 | 不重取；重新验证结果、授权和库存，才可尝试写入 |
| writing | 已在调用写库前落盘；可能写入部分或全部 | 只核验已有内容；全部匹配才 committed，否则保留现场，不再写、不删除 |
| committed | 冻结结果已读回核验 | 跳过，不重复取数或写入 |

所有 writing 状态先于新股票处理。未解决的不确定写入阻断新请求。只看行数相同不能确认成功；`matches` 必须比较实际业务内容。缺失文件、内容哈希不符、计划变化、软链接/错误权限均拒绝，不重建“丢失”的状态。

此核心偏保守：写库调用之前宕机也可能留下 writing；即使核对发现完全未写入，也不会自行重试。后续可另行设计有证据的人工恢复操作，不能通过改 JSON/删状态文件绕过。

## 适配接口的强制边界

`advance(identity, adapter, max_items=...)` 的 adapter 由调用方显式提供，本轮只有测试替身：

1. `authorize(plan_hash, item, action)`：每次返回严格 True 才能继续；必须检查真实授权范围、到期、STOP 和调用身份。这是只读检查，可被多次调用，不得在该函数里扣预算。
2. `preflight(item)`：对原同源序列与唯一索引做只读校验，返回与冻结观察一致的哈希；不能将数据库错误解释为零条记录。
3. `fetch(item)`：必须通过逐请求计数、限频、许可检查的出口；daily 与 adj_factor 每次实际 HTTP 调用都要先持久化扣减。批次核心的一次 fetch 不等于一次 HTTP 请求，不能拿 `fetch_attempts=1` 代替请求账本。
4. `validate(item, payload)`：完整验证来源、标的、日期范围、日线契约、单位、复权及数据完整性；返回严格 True。恢复后会再次调用。
5. `write(item, payload)`：只允许写冻结内容，复用历史契约校验与幂等存储。新接入不能隐式改变生产数据口径或迁移旧序列。
6. `matches(item, payload)`：只读检查全部目标业务内容及未预期的改动，严格 True 才代表完成。不能仅检查任务状态、写入计数或最新日期。

传给适配器的 item/payload 都是副本，适配器修改参数不会污染已冻结内容。检查发生后授权或库内容仍可能变化：真实出口必须在实际请求处再检查；真实写入侧必须落实写者隔离和必要的条件校验。工作目录锁仅覆盖使用同一规范路径的本核心调用者，不声称锁住旧 worker、外部导入或任意其他目录中的执行器。

计划里的 quota 只作输入前提，不是授权。未知额度的计划不能创建执行批次。单测使用明确标记的 synthetic 配额，不能复制成生产许可。原手动出口到期、STOP 及旧限额锁存均未改变。
