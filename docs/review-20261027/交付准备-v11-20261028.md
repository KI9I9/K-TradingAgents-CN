## 本轮关闭的预检漏洞

### 1. docker exec 的环境不能代替服务启动环境

`migration_production_entrypoint.py` 在自身进程中 `os.environ.update(env)`，Docker inspect 的 Env
和另一个 exec 进程不会自动得到该注入结果。旧冒烟可能在服务写闸打开时报告关闭。

新工具 `deploy/quote_guard_runtime.py`：

1. 先比对实际入口字节的完整 SHA256；本包预期为
   `d75d2ac13363b5b46284684d39c05c22c79886903174a0e09552175537ecf82b`。
2. 使用已校验的同一份入口字节，仅调用其中的私密文件读取和封印验证函数，不调用 `main()`。
3. 校验 runtime/context/approval，再按与入口一致的顺序合成继承环境与注入环境。
4. 写闸缺省关闭；`QUOTES_INGEST_ENABLED` 和 `AKSHARE_QUOTES_SYNC_ENABLED` 必须显式关闭。
   后两者默认开启，因此缺字段不能算关闭。错误拼写也拒绝，不利用宽松布尔解析掩盖错误。
5. 报告只含三个开关的布尔结果/来源和哈希，不输出配置、凭据或异常原文。

`quote_guard_smoke.py --installed` 现在强制要求入口路径和哈希，并在重建环境后检查实际导入的契约模块。
检查本身不访问数据库、网络，不修改封印文件；只有检查子进程的内存环境发生变化。
显式检查不依赖 Python assert，因此 `-O`/`PYTHONOPTIMIZE` 不能绕过。

**证明范围**：启动配置重建 + 检查子进程内的模块行为。不是运行中业务进程的实时状态证明。
仍须核对容器实际入口/命令、运行代码哈希、封印哈希、重建成功和当前调度/API 结果。
偏好恢复可能覆盖任务初始暂停状态，配置检查不能代替偏好和最终任务状态。

实际执行时须把相邻的两个检查脚本放在同一检查目录；不能继续用 v10 的“仅把 smoke 脚本经 stdin 送入”命令。
容器内入口路径须取自已核对的 inspect，不能猜路径。检查模式示意（参数需以本轮证据填入）：

```text
python3 -B <检查目录>/quote_guard_smoke.py --installed --app-root /app \
  --runtime-entrypoint <容器实际入口文件> \
  --expected-entrypoint-sha256 d75d2ac13363b5b46284684d39c05c22c79886903174a0e09552175537ecf82b
```

不要通过 `docker exec -e QUOTES_WRITE_ENABLED=0` 等手段给检查注入期望结果。
本地测试构造的假封印和凭据仅存在于临时目录；未读取实际封印。

### 2. Compose 校验不再只比较几个字段

`deploy/verify_compose_merge.py` 现在对比所有顶层和服务字段。
除了显式列明的新增挂载，其余任何差异都拒绝，包括网络、权限、健康检查、重启策略、旧挂载子选项。
新增项必须精确匹配源、目标、bind 类型、只读及 `create_host_path=false`，未知选项和重复目标也拒绝。
诊断只报字段/键名，不打印环境值、命令内容或其他可能包含凭据的值。

接口发生不兼容变更：

```text
python3 verify_compose_merge.py before.json after.json \
  --allow backend:/app/app/routers/paper.py=<固定发布目录>/app/routers/paper.py \
  ...其余 5 个 backend 挂载... \
  --allow frontend:/usr/share/nginx/html=<固定发布目录>/frontend-dist \
  --running backend=before-backend.json --image backend=before-backend-image.json \
  --running frontend=before-frontend.json --image frontend=before-frontend-image.json
```

- `--running` 必须与同服务的 `--image` 成对；旧版单路径 `--running file.json` 已废弃。
- 镜像证据必须对 before 配置中的完整 image 引用执行 `docker image inspect` 得到，不能只 inspect 旧容器 ID。
- 比较运行 Image ID，按镜像默认值解释未声明的 entrypoint/command；显式空值不再被当作未声明跳过。
- 校验容器继承环境，以及 bind/具名 volume 的源、目标、读写属性。未解析的 env_file、匿名/未知挂载类型拒绝。
- 不提供 `--running` 时只验证 before/after 差异，输出会明确 `running_checked=none`，不能用于生产验收。
- **运行态比对范围仍有限**：未把所有 HostConfig 字段与 Compose 反向等价转换，不宣称全面运行漂移检查。
  完整 before/after 服务配置相同，也不等于当前容器所有运行参数已证明相同。
- 同名 tag 的镜像 ID 在采样时相同不保证之后不被重新指向。维护窗口内禁止拉取/打标；
  重建使用 `--pull never`，重建后再次比对 Image ID。不一致即停止验收。

## 部署与回滚必须维持的顺序

- 先验证完整包、前后端基线、配置和任务证据；漂移即停。
- 正式部署须单独授权。先停止 backend 并确认退出，再采集停机基准和备份 3 个源；备份非空不得覆盖。
- 原地覆盖 3 个源，核验 inode 未变且目标哈希正确；新挂载文件已全部安装并核验后才能重建。
- 前后端均使用保存的完整原链、项目目录/名、profile，再附加本包 override。
  重建使用 `up -d --no-deps --force-recreate --pull never <service>`，不启用任务，不改变封印。
- 验证镜像 ID、9 个运行文件哈希、实际入口、启动配置重建、健康、最终任务状态、记录快照与前端 HTTP 资源。
- 覆盖开始后若失败，先确保故障 backend 停止。能证明持久化偏好及基线启动配置不会恢复供给，
  才允许恢复 3 个源并用原链重建；证明不了就保持停止。前端单独恢复原链。
- 恢复时验证的是实际目标源的基线哈希与 inode，不是只验证备份本身。
  回滚到基线会移除新护栏，无法承诺仍保持本次隔离；绝不自动恢复数据库。
