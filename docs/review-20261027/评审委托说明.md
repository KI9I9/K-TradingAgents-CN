## 一、系统背景

一套 A 股量化分析 + 模拟交易系统，后端 Python (FastAPI) + MongoDB，容器化部署。

**关键架构特征**（会影响你的判断）：

- 生产容器不是「按仓库代码构建镜像」，而是**镜像 + 9 个 bind mount 补丁文件**叠加运行。镜像内的同名文件是旧的。
- 所以「仓库代码」「镜像内代码」「生产实际运行的代码」三者互不自动相等。方案里所有行号以生产挂载文件为准。
- 生产是**唯一写入方**，没有主从、没有灰度。

**数据链路**：

```
akshare（东财主源 / 新浪、腾讯备用源）
    ↓ 定时任务（18:00 历史同步、盘中每 30 分钟行情快照）
MongoDB：stock_daily_quotes（日线，138 万条）
        market_quotes（实时快照，用于下单校验）
        etf_daily_quotes（ETF 日线）
    ↓
模拟交易下单接口（校验价格必须落在当日 high/low 区间内）
```

### 当前可用状态（避免误判严重程度）

- 历史日线数据**是完整的**：2026-10-26 有 5,566 只，OHLC/涨跌幅/成交量单位均已核验
- 受影响的**只有模拟交易的下单前价格校验**
- `159865` 已通过手工补入一条行情，可正常下单；其余标的不可
- 即：**不是系统瘫痪，是一个功能模块缺数据供给**

### 时间敏感性（影响你的取舍建议）

方案产出时间为 2026-10-27 01:00 CST（周二凌晨）。下一个交易日 09:30 开盘。

- 若在开盘前完成阶段 B：当日 09:30 起就有实时行情（任务每 30 分钟一次）
- 若拖到开盘后才完成：当日盘中前几十分钟仍不可下单；具体损失取决于完成时点
- 若只做阶段 A：**立刻**全市场可下单，但数据是 10-26 收盘快照，且盘中不会被刷新

请在做取舍时把「修复时点 vs 交易日」纳入考虑，并明确你倾向的时间安排。

## 四、需要你回答的问题

### 主问题

模拟交易对**除 159865 外的任何标的**下市价单，都会报：

```
无法获取股票 XXXXXX (CN) 的当天价格区间，无法验证指定价格
```

我方归因为**四层开关叠加**导致行情表为空，并给出两阶段方案。请判断这个归因和方案是否正确、完整。

### 具体判断项（请逐条给结论）

1. **阶段 A（纯数据回填）该不该做？**
   做法：删掉现有唯一 1 条行情 → 从 `stock_daily_quotes` 聚合 2026-10-26 全量（5,566 只）批量 upsert 进 `market_quotes` → 补回 ETF。
   副作用：灌入的是**收盘快照**，盘中下单会用前一日 high/low 校验，指定价格可能被误拒；市价单成交价会是昨日收盘价。
   **问：这个副作用可接受吗？还是应该跳过 A，直接等 B 生效后由实时数据填充？**

2. **阶段 B 的代码改法选哪个？**
   `akshare_sync_service.py:434` 的标的内联查询 `{"list_status": "L"}` 恒返回 0 只（`stock_basic_info` 11154 条全无该字段）。同文件 786 行已有修好的 `_get_all_listed_symbols()`（用 `$ne: "D"` + 去重）。
   - 改法一：复用 `_get_all_listed_symbols()` → 标的池 5,577（去重）
   - 改法二：内联改 `$ne: "D"` → 标的池 11,154（含双源重复）
   **问：改法一是否引入新问题？5,577 这个数量是否覆盖全部应同步标的（含北交所 351 只）？**

3. **ETF（159865 这类）是否纳入本次修复？**
   我方发现行情任务的取数走 `ak.stock_zh_a_spot()` / `stock_zh_a_spot_em()`，**都是纯 A 股、不含 ETF**。所以即使 B 全部生效，ETF 也不会被自动更新。备选是打开 `etf_sync`（写 `etf_daily_quotes`，T-1 日线），但我方**未深入核查它的标的来源逻辑**。
   **问：纳入还是拆到下一次？如果有风险，风险在哪？**

4. **`market_quotes` 非空会阻断系统自带的整库回填，这个判断对吗？**
   依据 `quotes_ingestion_service.py:440` 的 `backfill_from_historical_data()`：集合为空才导入，不为空只做 `_fix_missing_volume()` 后 return。
   **问：我方理解是否正确？若正确，阶段 A 先删后灌的顺序是否必要？**

5. **重启与部署方式是否安全？**
   计划：原地覆盖挂载源文件（保留 inode）→ `docker restart backend`（约 30 秒）→ 用 API `POST /api/scheduler/jobs/akshare_quotes_sync/resume` 打开开关。
   **问：是否有遗漏的前置检查或更低风险的替代路径？**

## 五、环境铁律（**不要建议违反这些**）

| 约束 | 原因 |
|---|---|
| **不得修改 `runtime-config.json`** | 其 SHA256 被 `launch-context.json` 的 `runtime_file_sha256` 校验，改一字节即 `raise ValueError('Launch context mismatch')`，且异常被 `except BaseException` 吞成一行 JSON（日志驱动为 none），表现为 **Exit=1、0.24 秒静默退出、零日志**。2026-10-25 已因此造成一次生产中断 |
| **不得修改 `launch-context.json`** | 同上，它是封印基准 |
| **不得建议打开 `TUSHARE_*` 任何任务** | tushare 出站闸门 `STOP` + `permit.json phase=blocked` 是硬锁，代码注释明确「无自动或 CLI 移除」；且该通道写入单位是「股」而库标准是「手」，放开会重新制造 100 倍污染 |
| **不得建议全量重刷历史数据** | 与本次问题无关，且北交所 `amount` 缺口是数据源限制，重刷修不掉 |
| **不得建议修改 `paper.py` 的价格校验逻辑** | 该逻辑本身合理（指定价格必须落在当日区间内），问题在数据供给 |
| **不得建议直接改 DB 绕过校验** | 应通过 API 或服务层 |
