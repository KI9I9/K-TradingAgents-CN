## 10. 附带发现：`_is_data_fresh` 的偏差方向与我此前记录**相反**

```python
# app/worker/akshare_sync_service.py:305
if updated_at.tzinfo == timezone.utc:
    updated_at = updated_at.replace(tzinfo=None) + timedelta(hours=8)
...
now = datetime.now()          # 容器内 = CST
time_diff = now - updated_at
```

- 全仓 `tz_aware` **0 命中** → pymongo 默认返回 **naive UTC** datetime。
- 写侧 `_bulk_upsert` 写的是 `datetime.now(ZoneInfo("Asia/Shanghai"))`（aware）→ BSON 存的是 UTC。
- 读回来是 **naive UTC**，`tzinfo is not None` 不成立 → **不走 +8 分支** → 直接与 `now()`（CST）相减 → **恒定偏老 8 小时**。

实测印证：159865 的 `updated_at` 写入于 00:15 CST，01:39 检查时按 naive 相减为 **9h24m**（真实 84 分钟）。

后果（方向与我旧记录相反）：
- `minutes=15` 判定 → **永远判「不新鲜」** → 每轮都重拉（浪费调用、易触发限频），而不是「全部跳过」；
- `hours=24` 判定 → 判「新鲜」→ 跳过；
- 现在的 `akshare_quotes_sync` 路径因 `updated_at` 字段压根没被写入（批量分支不返回该键）而恒为 `None` → `_is_data_fresh` 直接 `False`，8 小时偏差尚未显形。

`QuotesIngestionService` 路径**不调用** `_is_data_fresh`，所以打开它不受此缺陷影响 —— 这是它比备用任务更优的又一理由。

## 13. 待你决策的三个部署选项

| 选项 | 做法 | 优点 | 缺点/风险 |
|---|---|---|---|
| **A（推荐）** | 重新封印 `runtime-config.json`，置 `QUOTES_INGEST_ENABLED=true`；同时 `QUOTES_BACKFILL_ON_OFFHOURS=false` 首启 | 走的正是写全字段的适配器（`akshare_adapter.get_realtime_quotes` 返回 close/open/high/low/pre_close/pct_chg/amount/volume），**不需改 provider**；Tushare 实时接口在该服务内硬禁用，不碰出站闸门 | **要动封印配置**（runtime-config + launch-context SHA + approval 三件套），比换挂载文件重 |
| **B** | 只打开 `akshare_quotes_sync`（先部署字段契约修复 + cron 修正） | 不动封印，只换挂载文件 | 30 分钟粒度太粗；休市期 `backfill` 会用昨收冒充今日；且 `_is_data_fresh` 8h 偏差会显形 |
| **C** | A + B 都开 | 覆盖最全 | **危险**：两套写入器字段口径不同且都 upsert 同一 `code`，会复现「close/high/low 保留旧值、其余被覆盖」的混合脏数据，正是最难查的错价场景。**不建议** |

无论选哪个，**建议同时做**（与选项正交，纯消费侧护栏）：

- `paper.py::_get_today_price_range` 增加校验：`trade_date == 今日` 且 `updated_at` 在 N 分钟内，否则视为「无区间」并明确报「行情数据未就绪」；
- `paper.py::_get_last_price` 增加 `stock_daily_quotes` 最新日 K 回退，并在返回时标注数据日期。

这两处能把「静默用错价成交」降级为「明确拒绝下单」，即使上游再出问题也不会产生错误成交记录。
