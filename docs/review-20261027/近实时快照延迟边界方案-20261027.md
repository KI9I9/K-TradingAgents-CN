# 近实时快照的延迟边界方案（按 King 2026-10-27 决策实现）

- 代码：`f403f29`
- 执行单：`执行单-行情修复部署与回滚-v5-20261027.md`
- 决策：接受「有明确延迟边界的近实时快照」用于模拟成交；**不打开开关式放行，不伪造 `quote_time`**
- 生产：零写入、零重启、零启停

---

## 1. 落点：把边界写成数据，而不是一个布尔

上一版是 `ALLOW_FETCH_TIME_AS_QUOTE_TIME = True/False`——**已删除**。那个开关的问题是：一旦打开，「多新算新」由代码常量决定，用户看不到、也无法按标的区分。

现在每一条行情记录自带四个字段：

| 字段 | 含义 | 谁写 |
|---|---|---|
| `quote_time` | 上游声明的**行情发生时间**；没有就**不存在这个键**，绝不填采集时间 | 写入侧透传 |
| `quote_time_source` | `upstream` 或 `fetch` | 写入侧 |
| `fetched_at` | 本次**采集**时刻（aware，+08:00） | 写入侧 |
| `snapshot_interval_seconds` | 写入方声明的**刷新周期** | 写入侧（当前 1800） |

消费侧据此计算：`允许延迟 = 声明周期 + 120s 余量`，且不超过硬上限 2400s。

---

## 2. 准入条件（四条同时满足）

1. `trade_date` == 今日（`YYYY-MM-DD` 与 `YYYYMMDD` 都接受）
2. `quote_time_source == "fetch"`（有 `quote_time` 的走上游通道，不在此列）
3. 当前时间在 **09:30–15:30**（`outside_snapshot_session` 之外一律拒绝）
4. `fetched_at` 可解析，且 `0 ≤ now - fetched_at ≤ 允许延迟`

任一不满足即拒绝，原因码区分：`trade_date_mismatch` / `quote_time_missing` / `outside_snapshot_session` / `snapshot_interval_invalid` / `snapshot_too_old` / `fetched_at_missing`。

**上游 `quote_time` 优先级最高**：只要有，就按 30 分钟上限判，采集时间不参与——避免「上游说 14:00、我们 14:20 才拿到」被当成新行情。

---

## 3. 参数（都可追溯到代码常量）

| 参数 | 值 | 常量 |
|---|---|---|
| 默认快照周期 | 1800s | `DEFAULT_SNAPSHOT_INTERVAL_SECONDS` |
| 延迟余量 | 120s | `SNAPSHOT_DELAY_MARGIN_SECONDS` |
| 允许延迟上限（硬） | 2400s | `MAX_SNAPSHOT_INTERVAL_SECONDS` |
| 上游行情时间上限 | 1800s | `DEFAULT_MAX_QUOTE_AGE_SECONDS` |
| 快照可用时段 | 09:30–15:30 | `SESSION_OPEN` / `SNAPSHOT_SESSION_END` |
| 日线回退起点 | 15:05 | `DAILY_FALLBACK_AFTER` |

**声明周期超限直接拒绝，不自动截断。** 理由：若允许截断，写入方声明「24 小时」也会被静默当成 40 分钟，边界就失真了。宁可报 `snapshot_interval_invalid`。

### 刷新频率的真实性风险

允许延迟是「声明周期 + 余量」，所以**声明必须与实际 cron 一致**：

- 当前 `AKSHARE_QUOTES_SYNC_CRON = */30 9-15 * * 1-5` → 30 分钟，写入侧 `snapshot_interval_seconds = 1800` 与之对齐。该值在生产**尚未修正**（`1-5` 在 APScheduler 里是周二至周六），本次随 `config.py` 覆盖改为 `mon-fri`，周期不变。
- 若将来把 `QUOTES_INGEST_ENABLED` 那条 6 分钟链路打开，**必须同步改 `self.snapshot_interval_seconds`**，否则会用 30 分钟的边界给 6 分钟的数据放行——边界变松，等于偷偷放宽。
- 这条已写进执行单 §0.2，作为部署检查项。

## 4. 用户提示

成交回报新增两个字段：

```json
{
  "order": { "...": "...", "pricing_basis": {
      "source": "fetch",
      "as_of": "2026-10-27T09:40:00+08:00",
      "delay_seconds": 1200,
      "max_delay_seconds": 1920,
      "notice": "模拟成交按 09:40:00 采集的行情快照定价，该快照最大延迟约 32 分钟；非交易所逐笔成交价。"
  }},
  "pricing_notice": "模拟成交按 09:40:00 采集的行情快照定价，该快照最大延迟约 32 分钟；非交易所逐笔成交价。"
}
```

- `pricing_basis` 落库到 `paper_orders`，事后可追溯「这笔单按什么价、多新的数据成交」。
- 日线通道的 `notice` 是「模拟成交按当日收盘价定价（非盘中实时价）」。
- 上游 `quote_time` 通道 `notice` 为 null，不打扰用户。
- 取 `pricing_basis` 失败只记日志，**不影响成交**（已加 try/except）。

## 5. 失败不续期

- 不完整快照（缺 close/high/low 或非有限值）→ `prepare_quote_write` 返回 `None`，调用方**不写库**。
- 于是旧记录的 `close/high/low`、`trade_date`、`fetched_at`、`updated_at` **全部保持原值**。
- 旧时间一旦超出边界，消费侧自然拒绝——不需要额外「失效标记」。
- 测试用 `$set` 合并语义验证：拒写后旧记录逐字段不变，且 `quote_is_usable` 仍为 False。

## 8. 与上一版的差别（为什么这不是「换个名字打开开关」）

| 维度 | 上一版 `ALLOW_FETCH_TIME_AS_QUOTE_TIME` | 本版 |
|---|---|---|
| 边界来源 | 代码常量（30 分钟），写死 | 数据字段（`snapshot_interval_seconds`），随写入方声明 |
| 是否可解释 | 不能，用户不知道多新 | 能，回报里带 `as_of`/`delay`/`max_delay` |
| 是否可拒绝 | 只能整体开/关 | 按记录逐条判定，超期即拒 |
| 交易时段 | 不检查 | 强制 09:30–15:30 |
| `quote_time` | 仍可能被采集时间顶替 | **不存在该键**，不伪造 |
| 上游时间优先 | 无此概念 | 有则优先，采集时间不参与 |

## 9. 残余缺口（未修，别当成已完成）

1. **上游行情时间仍然没有**。AKShare 快照不提供逐行时间，所以「32 分钟」是采集延迟的上界，不是报价真实年龄的上界。上游若返回缓存 1 小时的旧报价，本方案仍会按「采集后 32 分钟内」放行——这是接受 ③ 时明确承担的代价。要根治只能接带 `trade_time` 的来源（Tushare `rt_k`）。
2. **仍未执行真实 provider**（离线无 akshare/pandas），provider 侧只改了成交量单位一行，靠纯函数测试覆盖换算。
3. **仍未调用真实 `paper.py` 取价函数**（依赖 fastapi/motor），只测了下沉后的判定与 `pricing_basis`。
4. **空池/跳过未测同步入口粘合层**，只测了 `build_failure_stats` + 真实 `outcome()`。
5. **`_is_data_fresh` 8 小时偏差未修**，仍被 `sync_realtime_quotes` 调用。
6. **`_read_cache()` 只取 source**，未校验同条缓存的 `fetched_at`/日期一致性（上一轮评审已指出，本轮未改）。

## 10. 需要评审确认的三点

1. 「允许延迟 = 声明周期 + 120s、硬上限 2400s」这组参数是否合理？特别是 30 分钟周期下 32 分钟的边界。
2. 交易时段限定 09:30–15:30（含收盘缓冲）是否合适？午休 11:30–13:00 期间，11:30 采集的快照在 12:30 就超期，会造成午后开盘前 30 分钟不可成交——这是否可接受？
3. ETF 明确不支持盘中，是否需要在产品文案上单独提示，还是等标的池扩容后一起做？
